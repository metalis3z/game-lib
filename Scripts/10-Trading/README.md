# 10 - Trading

Player-to-player trading taken from the unpacked games: sending a trade request, building two offers, a
ready / confirm handshake, and the server-side swap. There are three flavours: same-server trades
(brainrot-lab, smash-egg-for-animals, rcu-roller, punching-simulator, uno), cross-server trades where the
two players are on different servers (trade-system, steal-a-brainrot, the removed smash-egg version), and
market-style trading (rcu-roller booths, steal-a-brainrot NPC trader). Most comments in the source files
are in French or Spanish. The headers are in English. The three files in `_patterns/` are clean, standalone
modules that combine the best ideas. Start with those if you are building your own system.

## Techniques seen across games

- **Server owns the trade, the client only asks.** Every good example keeps sessions in a server table keyed by player (`trades[player] = session`, with the same table stored for both players). Clients send intents (`Add id`, `Ready`, `Confirm`). The server re-derives everything else and pushes a full state snapshot back to both clients. The partner's offer is sent as display data only, never as instance references the client could misuse (see brainrot-lab `buildStateForPlayer`).
- **Any change resets readiness.** Adding or removing an item, or the item disappearing from the inventory, clears READY and CONFIRM on both sides. The safer games add a two-stage handshake (READY, then CONFIRM) with a server-enforced delay between the two: 3s in smash-egg and 8s in steal-a-brainrot. The client countdown is only cosmetic, and the server checks the time again on Confirm.
- **Validate again at execution, then swap all-or-nothing.** The swap re-reads the real inventory and checks each offered id: it still exists, it isn't offered twice, it isn't placed, equipped or being stolen, and both sides have room. Only then does it mutate anything, and it saves both players immediately (smash-egg `Execute`, brainrot-lab `executeTrade`, steal-a-brainrot snapshot). Items get fresh ids on the receiving side so ids never collide.
- **Locks against double use.** brainrot-lab sets an `InTrade` attribute, uno sets `SaveLocked` during the swap, rcu-roller removes listed items into escrow, and smash-egg's escrow version takes pets out of the inventory before delivering them. Pick one so an item can't be sold, fused or traded twice at the same time.
- **Cross-server trades need escrow plus an inbox.** MemoryStore holds the shared session (trade-system) and MessagingService carries requests and sync. The safe pattern is: lock on the sender's server, then deliver through a DataStore inbox that the receiver claims (smash-egg removed version). The other route is a master server that asks the remote server to `prepare` before it `execute`s (steal-a-brainrot). Writing to both players' data from one server is never safe.
- **Anti-spam everywhere.** Requests expire (15-60s) and have a per-sender cooldown. Edits have a per-player cooldown (2s in smash-egg and steal-a-brainrot). There is a cap on actions per second per player. Offers have a maximum size (9-100). Remote arguments are type-checked before use. Leaving the game cancels the trade and clears that player's pending requests in both directions.
